# Pulse BI: Real-Time NYC Taxi Operations Dashboard

## Final Project Presentation

---

## Slide 1: Title

### Pulse BI
### Real-Time NYC Taxi Operations Dashboard

**A web-based dashboard for monitoring taxi trips, revenue, distance, passengers, and payment methods.**

**Technology:** HTML, CSS, JavaScript, Node.js, WebSocket, and Progressive Web App (PWA)

---

## Slide 2: Project Introduction

- Pulse BI is a real-time business intelligence dashboard.
- It analyzes New York City taxi trip records.
- The dashboard receives data in batches of 5,000 records.
- A new batch is loaded every 5 seconds.
- Users can monitor taxi operations through a simple web interface.
- The application is designed for quick operational decisions.

---

## Slide 3: Problem Statement

Taxi organizations generate a large amount of trip data.

Without a live dashboard:

- It is difficult to understand current trip activity.
- Revenue changes may not be noticed quickly.
- Payment-method performance is harder to compare.
- Large CSV files are difficult to inspect manually.
- Important operational information is spread across raw records.

**The project solves this problem by converting raw taxi data into live, readable business metrics.**

---

## Slide 4: Project Objectives

The main objectives are:

1. Build a simple real-time analytics dashboard.
2. Process NYC taxi trip data in manageable batches.
3. Show total revenue and total trip count.
4. Display average trip distance and average fare.
5. Compare trips by payment method.
6. Show revenue changes across batches.
7. Provide a responsive and installable web application.
8. Support live updates without refreshing the page.

---

## Slide 5: Data Source

- **Batch size:** 5,000 records
- **Source type:** Local CSV dataset prepared for the application

Each batch contains summarized values used by the dashboard.

---

## Slide 6: System Architecture

### Main components

1. **Dataset**
   - Provides NYC taxi trip information.
   - Data is stored locally in batch format.

2. **Node.js server**
   - Loads one data batch at a time.
   - Serves the web application.
   - Provides the `/api/taxi` API endpoint.
   - Sends live updates through WebSocket.

3. **Web dashboard**
   - Displays key performance indicators.
   - Shows payment-method analysis.
   - Renders the revenue trend chart.

4. **Service worker**
   - Caches application files.
   - Supports offline loading of the application shell.

### Data flow

`Local dataset → Node.js server → REST API/WebSocket → Browser dashboard`

---

## Slide 7: Application Workflow

1. The server starts and loads the prepared batch dataset.
2. The first 5,000-record batch is selected.
3. The server creates a current data snapshot.
4. The browser requests the initial snapshot through the API.
5. The browser opens a WebSocket connection.
6. The server broadcasts a new snapshot every 5 seconds.
7. The dashboard updates its cards, table, bars, and chart.
8. After the last batch, the application continues from the first batch.

The total revenue generated by trips in the current batch.

The number of taxi records included in the current batch.

### Records in current batch
The number of records currently being analyzed and the batch range.

### Average trip distance
The average distance traveled per taxi trip.

Additional calculated information includes:

- Average fare per trip
- Average passengers per trip

## Slide 11: Revenue Trend Analysis

- The dashboard stores recent batch results in the browser.
- Each chart point represents one 5,000-record batch.
- The chart displays revenue across recent batches.
- Upward movement indicates increasing batch revenue.
- Downward movement indicates decreasing batch revenue.
- The dashboard explains the percentage change between the latest two batches.

This gives users a quick view of whether revenue is strengthening or weakening.

## Slide 13: API and Communication

### REST endpoint

`GET /api/taxi`

Returns the current taxi data snapshot as JSON.

### WebSocket endpoint

`/ws`

Used for live updates from the server to connected browsers.

### Update interval

The server refreshes data every 5 seconds.

### Error handling

- The server reports loading errors in the console.
- The API returns an error response if data is not ready.
- The browser reconnects when the WebSocket connection closes.
- Cached application files support continued shell access.

## Slide 17: Limitations

- The current application uses prepared local batch data.
- The dataset represents January 2015 records.
- The dashboard does not yet include live GPS locations.
- There is no user login or role management.
- Historical data filtering is limited.
- The current analytics are descriptive rather than predictive.
- The dashboard depends on the configured backend URL when deployed.
